## はじめに

本記事は、検証用の仮想マシン（以下、テスト VM）を GitHub Actions 経由で貸し出す仕組みを説明します。
対象の環境は、Proxmox VE で仮想マシンを作り、IP アドレスの管理に NetBox を使う構成です。

前提は次のとおりです。

- 設定変更を本番に当てる前に、テスト VM で試す運用にしている
- 管理者以外の作業者は、Proxmox と NetBox の資格情報を持たない
- 資格情報を持たない作業者でも、テスト VM を自分で用意できる必要がある

この仕組みでは、作業者は GitHub Actions のワークフローを実行するだけでテスト VM を借ります。
期限は既定で 8 時間であり、期限が来た VM は自動で消えます。
作業者に Proxmox と NetBox の資格情報を渡すことはありません。

## 全体の流れ

登場する要素は次の 4 つです。

- 作業者は GitHub Actions のワークフローを実行する
- ワークフローは、資格情報を持つ自己ホスト型のランナー上で動く
- ランナー上のスクリプトが Terraform を実行し、Proxmox に VM を作り、NetBox に登録する
- 期限の管理は、ランナー上に置く貸し出しの記録で行う

ワークフローの名前は `test-vm-lease` です。
処理の実体はリポジトリ内のスクリプトであり、ワークフローは入力を受け取ってスクリプトを呼ぶだけです。
ワークフローの権限は、リポジトリの読み取りだけにしています。

同時実行は 1 件に限ります。
VM ごとの Terraform の state をランナーの同じ置き場で扱うためです。
state は VM の名前ごとに分けて置き、頼んだ人と期限は同じ場所の `lease.json` に記録します。

## 資格情報を持たせない設計

資格情報は、ランナー側だけが使います。
作業者が入力するのは、VM の名前、自分の SSH の公開鍵、期限などの項目だけです。
入力はシェルに直接埋め込まず、環境変数でスクリプトに渡します。

テスト VM の作り方にも、資格情報の範囲を狭める工夫があります。
本番の VM は、cloud-init の user-data をスニペットとして Proxmox のノードに置く方法を使います。
スニペットは Proxmox の API では上げられず、プロバイダがノードへ SSH して置く必要があります。

テスト VM ではスニペットを使わない設定にしています。
そのため、作成は API だけで完結し、プロバイダがノードへ SSH することはありません。
この選択により、Proxmox への認証を API トークンに切り替える道が開けます。
ノードへの SSH の経路を持たない分、漏れた場合の影響も小さくなります。

テスト VM のパスワードは、VM ごとにランダムに生成します。
本番の VM のパスワードは使いません。
入るための鍵は、頼んだ人の公開鍵と、本番の Ansible 用の鍵です。

## 貸し出しの操作

操作はワークフローの入力 `action` で選びます。
種類は `create`、`destroy`、`list` の 3 つです。

コマンドラインからは `gh` コマンドで実行します。

```bash
gh workflow run test-vm-lease.yml -f action=create -f name=nginx-test01 \
  -f ssh_public_key="$(cat ~/.ssh/id_ed25519.pub)"
gh run watch
```

作成が終わると、ジョブの Summary に FQDN、IP アドレス、期限が出ます。
GitHub の画面の Run workflow からも同じ操作ができます。

作成時の主な入力は次のとおりです。

- 名前は英小文字、数字、ハイフンで書き、`test` を含める必要がある
- 期限は `hours` で 1 から 24 の範囲で指定する
- イメージは Debian、Ubuntu、Rocky Linux の cloud image から選ぶ
- ネットワークは 3 種類のセグメントから選ぶ
- CPU、メモリ、ディスクの大きさは入力で変えることができる

既定値は、CPU 2 コア、メモリ 2048 MB、ディスク 16 GB です。
2 枚目のディスクが必要な場合は、`extra_disk_size` で大きさを指定します。

名前には制限があります。
NetBox に既にある名前と、他の人が CI で使っている名前は使えません。
検証に使わない名前が残らないよう、名前に `test` を含める決まりにしています。

## 延長と返却

延長は、同じ名前でもう一度 `create` を実行します。
期限は、その時点から数え直します。

```bash
gh workflow run test-vm-lease.yml -f action=create -f name=nginx-test01 \
  -f ssh_public_key="$(cat ~/.ssh/id_ed25519.pub)" -f hours=24
```

延長のときに大きさや鍵を変えると、作り直さずに当て直します。
メモリなどを変えた場合は、VM は再起動します。

返却は `destroy` で行います。

```bash
gh workflow run test-vm-lease.yml -f action=destroy -f name=nginx-test01
gh workflow run test-vm-lease.yml -f action=list
```

消せるのは、頼んだ人と管理者だけです。
`list` は一覧を出す処理であり、期限の過ぎた VM があれば合わせて消します。

期限切れの削除は、スケジュール実行でも行います。
ワークフローは毎時 23 分に動き、期限の過ぎた VM を消します。
そのため、消し忘れた VM が残り続けることはありません。
削除では、VM 本体に加えて、NetBox の VM と IP、Proxmox の HA リソースもまとめて消えます。

作成は 1 回につき 1 台です。
複数の VM が必要な場合は、名前を変えてそれぞれ作成します。

## 本番に影響させないための作り

テスト VM は本番のインベントリに載ります。
そのままだと本番の処理の対象になりかねないため、次の対策を入れています。

- テスト VM には NetBox のタグを付けない
- 本番の play はタグで対象を選ぶため、テスト VM はどの play の対象にもならない
- 対象を指定して実行する場合だけ、テスト VM にロールを当てることができる
- 本番の初期設定の playbook は、既定ではテスト VM に流さない

初期設定を流さない方法は、向ける先を変えることです。
仮想マシンを作るモジュールは、作成直後に初期設定の playbook を実行する仕組みを持ちます。
テスト VM では、何もしないスタブの play に向けています。
ログにホストが一致しない旨が出るのが正常な状態です。

初期設定を流す入力も用意されています。
ただし、本番の監視に触れる処理も実行されるため、確かめたい場合だけ使います。

## 作業者側で秘密が読めないことへの対処

作業者の持つアクセストークンで読めるのは、全員が読めるプロジェクトだけです。
具体的には、NetBox の読み取り専用トークンなどです。
インベントリはそれで読めますが、設定ファイルに書かれた秘密は読めません。

ロールを当てるときは、読めない秘密を仮の値で上書きして実行します。
接続のたびに読まれるパスワードも、任意の値で上書きする対象です。
使う秘密だけを同じ方法で仮の値にします。

本番の証明書は秘密鍵ごと配るものなので、テスト VM には配りません。
証明書が必要な場合は、一時的な playbook で自己署名の証明書を同じパスに作ります。
検証が終わったら、VM と一時的な playbook の両方を消します。

## まとめ

要点は次の 3 点です。

- 作業者は GitHub Actions を実行するだけで、期限付きのテスト VM を借りることができる
- Proxmox と NetBox の資格情報はランナー側だけが持ち、作業者には渡さない
- 期限の過ぎた VM は毎時のスケジュール実行で自動で消える

資格情報を配らずに検証の手段だけを渡すことが、この仕組みの中心の設計です。
