## はじめに

本記事は、自宅環境で netboot.xyz を使い、PXE ブートで各種 OS のインストーラーやライブ環境を起動する構成を説明します。
対象は、実機と Proxmox VE 上の仮想マシンです。
中心となるホストは、ゲートウェイを兼ねる 1 台で、DHCP、TFTP、HTTP の配布をこのホストに集約します。

netboot.xyz は、iPXE のメニューから各種 OS のインストーラーやライブ環境を選んで起動できる仕組みです。
本記事の構成では、メニュー自体は boot.netboot.xyz から取得します。
ローカルに置くのは、ブートローダーと、起動直後に読み込まれるスクリプト、および一部の OS の配布ファイルです。

## 全体の流れ

起動の流れは次のとおりです。

1. クライアントはネットワークブートを選択し、DHCP でアドレスとブートファイル名を受け取る。
2. クライアントは TFTP でブートローダーを取得する。
3. ブートローダーはスクリプトを読み、Secure Boot の有無に応じてメニューを表示する。
4. 利用者はメニューから netboot.xyz、Ubuntu Server、Windows のいずれかを選ぶ。
5. 選んだ OS のファイルは、HTTPS または HTTP で取得する。

DHCP、TFTP、HTTP の役割は次のとおりです。

- DHCP は、アドレスの払い出しと、次に読むブートファイルの指定を担当する。
- TFTP は、起動直後の小さなブートローダーの配布を担当する。
- HTTP と HTTPS は、メニュー表示後のカーネル、初期 RAM ディスク、ISO イメージなどの配布を担当する。
- Windows のインストールでは、WinPE の起動後に SMB でインストールメディアを参照する。

## DHCP の設定

DHCP サーバーには Kea を使います。
Kea は、受けたインターフェースと DHCP の option 60 が PXEClient であることを条件に、PXE 用のクラスを割り当てます。
対象とするセグメントは、home、mgmt、intra、dmz の 4 つです。
対象外のセグメントには PXE 用のファイル名を返しません。

ブートファイル名は、DHCP の option 93 が示すアーキテクチャで選びます。

| option 93 | 種類 | 渡すファイル |
| --- | --- | --- |
| 0 | レガシー BIOS | netboot.xyz のレガシー向けファイルである |
| 7、9 | UEFI x86_64 | Microsoft の署名を持つ shim 経由の iPXE である |
| 11 | UEFI arm64 | Microsoft の署名を持つ shim 経由の iPXE である |

表にないアーキテクチャにはファイル名を返さないため、その機器のネットワークブートは失敗します。
TFTP サーバーのアドレスは、各サブネットの next-server でゲートウェイホスト自身を指定します。

ファイル名の返し方には注意点があります。
ファイル名は option 67 ではなく、BOOTP ヘッダの file 欄で返します。
古い UEFI PXE の実装には、option 67 を NUL 終端と見なし、後ろのデータをファイル名に含めるものがあります。
その場合、TFTP で File not found になるためです。

なお、iPXE は起動後に DHCP をやり直すが、ブートファイル名を読み直すことはありません。
そのため、同じ応答を受けてもブートローダーを繰り返し読み込むループにはなりません。

## TFTP の配布

TFTP サーバーには tftpd-hpa を使います。
配布ディレクトリは読み取り専用とし、ファイアウォールでは対象セグメントから 69/udp のみを通します。
配布するブートローダーは、netboot.xyz と iPXE の GitHub Releases から取得し、バージョンと sha256 を固定します。

UEFI 向けには、常に署名済みの shim を渡します。
DHCP の時点では Secure Boot が有効かどうかが分からないためです。
shim は、自身の名前から決まる iPXE 本体を読み、その iPXE が設定スクリプトを読み込みます。
スクリプトの中で Secure Boot の状態を確認し、行き先を分けます。

Secure Boot が無効な場合は、機能を絞っていない netboot.xyz の iPXE に乗り換えます。
Secure Boot が有効な場合は、netboot.xyz の公式の Secure Boot 用スクリプトでメニューを開きます。
Secure Boot が有効な環境で起動できる項目は、各ディストリビューションの署名済み shim を使う項目などに限られます。

## USB ドライバを持たない iPXE を使う理由

渡す iPXE は、USB のドライバを持たないビルドに統一します。
iPXE の標準ビルドは USB NIC と USB ホストコントローラーのドライバを持ち、USB コントローラーを掴むことがあります。
その場合、一部の環境ではファームウェア側の USB キーボードのドライバが外れ、メニューでキーが効かなくなります。
この現象は実機の UEFI で発生し、QEMU の OVMF や SeaBIOS では再現しませんでした。
代わりに、このビルドでは USB NIC からはブートできません。

機器ごとに NIC が認識されない場合は、Kea の予約で MAC アドレスごとにブートファイルを上書きします。

- BIOS で DHCP に失敗する場合は、ファームウェアの UNDI を使うビルドに切り替える。
- BIOS で USB NIC からブートする場合は、USB ドライバを持つビルドに切り替える。
- UEFI でファームウェアの NIC ドライバが正常に動かない場合は、iPXE 自身のドライバを使うビルドに切り替える。

切り替え先のビルドでも、読み込む設定スクリプトは同じで、メニューと Secure Boot の扱いは変わりません。

## メニューの項目

UEFI x86_64 では、起動後にローカルのメニューが表示され、30 秒で netboot.xyz に進みます。
BIOS と、Secure Boot が無効な arm64 では、メニューを出さずに netboot.xyz のメニューに進みます。

- netboot.xyz の項目は、boot.netboot.xyz のメニューを開く項目である。
- Ubuntu Server の項目は、公式サイトから取得するファイルでインストーラーを起動する項目である。
- Windows の項目は、ゲートウェイホストに置いた ISO からインストーラーを起動する項目である。

Ubuntu Server の項目は、ISO 全体をメモリに読み込んでインストーラーを起動します。
そのため、メモリは ISO の 2 倍以上が必要です。
ISO が約 3 GB の版では 4 GB で読み切れず、8 GB で起動したことを QEMU で確認しています。
ISO が約 4 GB の版では、10 GB 程度を用意します。

Windows の項目は、wimboot で WinPE を起動し、WinPE から SMB 共有の setup.exe を実行する構成です。
wimboot と WinPE のファイルは HTTP で配り、インストールメディアは読み取り専用の SMB 共有で配ります。
ファイアウォールでは、対象セグメントから 80/tcp と 445/tcp を追加で通します。

## Proxmox VE での利用

Proxmox VE の仮想マシンで PXE ブートを使う場合は、ブート順でネットワークデバイスを上げます。
起動時に Esc または F12 でブートメニューを開き、ネットワークブートを 1 回だけ選ぶ方法もあります。

注意点は次のとおりです。

- OVMF で PXE ブートする場合は、VirtIO RNG を付ける必要がある。
- 新しい OVMF は、乱数源のないゲストではネットワークブートの項目を表示しない。
- WinPE がドライバを持たない NIC では、SMB 共有に接続できない。
- Windows を入れる仮想マシンは、NIC を e1000e、ディスクを SATA にする構成が扱いやすい。
- 起動順はディスクを先にし、PXE は起動時のメニューで選ぶ運用にする。
- ネットワークを先にすると、インストール後の再起動でも PXE に戻り、入れ直しが続く場合がある。

intra と dmz の常設の仮想マシンは、固定アドレスを cloud-init で設定する構成です。
DHCP のプールは、PXE で OS を入れる機器がインストール中に使うためのものです。
インストールが終わったら、アドレス管理に登録し、固定アドレスに切り替えます。

また、両セグメントは MTU 9000 ですが、PXE 自体はこの影響を受けません。
DHCP と TFTP のパケットは小さく、TFTP のブロックサイズはクライアント側の MTU から決まるためです。
OS 起動後の MTU は、仮想マシンでは virtio が伝える値になり、物理マシン向けには DHCP の option 26 でも渡します。

## 自動インストールとの組み合わせ

この構成には、Ubuntu の自動インストールも組み込んでいます。
アドレス管理側で特定のタグを付けた機器は、PXE 起動時にメニューを出さず、無人で Ubuntu をインストールします。
同期用のスクリプトが 1 分ごとにタグを確認し、MAC アドレスごとの iPXE スクリプトと user-data を生成します。
user-data は HTTP で配るため、秘密情報は載せません。
インストール直後の利用者は、鍵認証のみでログインできる状態にします。
起動順をディスク先行にしておく点は、自動インストールでも同じです。

## 動作確認

起動したかどうかは、ゲートウェイホストの journal で追えます。
Kea と tftpd-hpa のログを確認し、TFTP の要求である RRQ が記録されているかを見ます。

```bash
journalctl -u tftpd-hpa -u kea-dhcp4-server --since today | grep -E 'RRQ|netboot'
```

TFTP で止まる場合は、ファイアウォールで 69/udp が通っているかと、tftpd-hpa が動いているかを確認します。
File not found の場合は、配布ディレクトリにファイルがあるかと、要求されたファイル名に余分な文字が付いていないかを確認します。

## まとめ

- DHCP はアドレスとブートファイル名の指定を担当し、アーキテクチャごとに渡すファイルを変える構成である。
- TFTP はブートローダーの配布のみを担当し、大きなファイルは HTTP と HTTPS で配る構成である。
- UEFI では署名済み shim を常に渡し、スクリプト側で Secure Boot の有無を判定する構成である。
- iPXE は USB ドライバを持たないビルドを使い、キーボードが効かなくなる問題を避ける構成である。
- Proxmox VE では VirtIO RNG の追加と、ディスク先行の起動順が要点である。
