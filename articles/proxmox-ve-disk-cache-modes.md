## 基本は none、条件の合う Ceph RBD には writeback

Proxmox VE の VM ディスクでは、同じ `writeback` を選んでも、ディスクの種類によって書き込み完了を返す場所が変わります。

| ディスク | 推奨設定 | 選ぶ理由 |
| --- | --- | --- |
| ローカル SSD | 既定の `none` | ホストのページキャッシュを通さず、VM が大量に書いた直後にホストに溜まった分の書き出しを待つのを避けられる |
| Ceph RBD | 基本は `none`、次の条件がそろえば `writeback` | VM ごとのキャッシュで書き込みを受けると、ゲストは毎回 Ceph の応答を待たずに次の書き込みに進める |

通常の書き込みは、データがメモリにある段階でも完了することがあります。
`fsync` は、アプリケーションが OS に「このファイルへの変更をストレージに保存してほしい」と頼み、完了の報告を待つためのシステムコールです。
その際、OS は必要に応じてディスクに flush を送り、キャッシュに残っているデータの書き出しを求めます。

RBD で `writeback` を勧める条件は次の 3 つです。

- その RBD イメージを使う VM は 1 台だけである
- アプリケーションが保存を保証したい時点で fsync を呼び、ゲスト OS がディスクに flush を送る
- 書き込みを何件か進めてからまとめて永続化する負荷がある

最初の 2 つはデータを守るための条件です。同じディスクを複数の VM で共有すると、各 VM のキャッシュは別の VM の書き込みを把握できません。
また、たとえば PostgreSQL の fsync を無効にすると、コミット時点でキャッシュに残っているデータを障害で失うおそれがあります。

最後の条件は性能のためです。1 件ずつ fsync の完了を待つ処理や読み取りが中心なら、今回の RBD の実測では `none` から変える利点はほとんどありませんでした。

## 5 つのキャッシュ設定で何が変わるか

ローカル SSD の場合、QEMU はホストのページキャッシュを使えます。そこに残っているデータは読み返すときにも使えます。
RBD の場合、キャッシュを持つのは QEMU が使う Ceph クライアントライブラリ (librbd) です。既定の設定では書き込みにだけ使います。

| 設定 | ローカル SSD | Ceph RBD |
| --- | --- | --- |
| `none` | ホストのページキャッシュを通さず SSD に書く | librbd のキャッシュを使わず Ceph に書く |
| `writeback` | ページキャッシュで書き込みを受け、flush で SSD への書き出しを待つ | librbd で書き込みを受け、flush で Ceph への書き出しを待つ |
| `writethrough` | ページキャッシュを使い、書き込みごとに SSD への永続化を待つ | librbd のキャッシュは有効だが、書き込みごとに Ceph への永続化を待つ |
| `directsync` | ページキャッシュを通さず、書き込みごとに SSD への永続化を待つ | librbd のキャッシュを使わず、書き込みごとに Ceph への永続化を待つ |
| `unsafe` | ページキャッシュで書き込みを受け、ゲストからの flush を無視する | librbd のキャッシュを有効にし、ゲストからの flush を無視する |

`writeback` では、通常の書き込みが完了してから flush が完了するまでの間に、障害で未書き出しのデータを失う可能性があります。
`unsafe` では fsync が成功してもこの可能性が残るため、データを失ってもよい一時的な VM に用途を限ります。

### QEMU のフラグとの対応

QEMU のキャッシュモードは、次の 3 つのフラグの組み合わせです。

- `cache.direct`: ホストのページキャッシュを通さない (`O_DIRECT`)
- `cache.no-flush`: ゲストからの flush を無視する
- `write-cache`: ゲストに「揮発性の書き込みキャッシュがある」と見せる。off にすると、ゲストは flush を送らず、QEMU が書き込みごとに書き込み完了を保証する

| `cache=` | `cache.direct` | `cache.no-flush` | `write-cache` |
| --- | --- | --- | --- |
| `none` | on | off | on |
| `writethrough` | off | off | off |
| `writeback` | off | off | on |
| `directsync` | on | off | off |
| `unsafe` | off | on | on |

VM を起動したときの qemu のコマンドラインを見て、実際にこの組み合わせになることを確かめました。

### ローカルのディスク

ローカルのブロックデバイスやファイルでは、`cache.direct` が off のモード (`writethrough`、`writeback`、`unsafe`) はホストのページキャッシュを通ります。
`writeback` の書き込みはページキャッシュに置いた時点で返り、ホストが順次ディスクに書き出します。ゲストが flush すると、それまでの書き出しの完了を待ちます。

### Ceph RBD

RBD ではホストのページキャッシュを使いません。
代わりに、QEMU の rbd ドライバが librbd のキャッシュ (`rbd_cache`) を `cache.direct` から決めます。

```c
/* block/rbd.c (要約) */
rados_conf_set(cluster, "rbd_cache", (flags & BDRV_O_NOCACHE) ? "false" : "true");
```

`ceph.conf` に `rbd_cache` を書いても、QEMU のこの設定で上書きされます。
キャッシュは qemu のプロセスの中にあり、未書き出し量のしきい値は既定で RBD イメージごとに 24 MiB です。[Ceph のキャッシュ設定](https://docs.ceph.com/en/tentacle/rbd/rbd-config-ref/#cache-settings)

librbd のキャッシュの振る舞いは `rbd_cache_policy` で決まり、既定値は `writearound` です。
書き込みはキャッシュに置いてすぐ返しますが、読み取りはキャッシュから返しません。
そのため、RBD ではどのモードでも読み取りは速くなりません。

もう 1 つ、`rbd_cache_writethrough_until_flush` (既定値 true) があります。
ゲストから最初の flush が来るまでは、librbd は書き込みごとに Ceph まで書いてから返します。
flush を送らない古いゲストでもデータを失わないための仕組みです。
今のゲストは起動してすぐ flush を送るので、計測には影響しません。

### RBD の writethrough

`writethrough` は `rbd_cache` を有効にするので、一見 `writeback` と同じに見えます。
実際には、`write-cache` が off なので、QEMU のブロック層が書き込みのたびに FUA (Force Unit Access) を付けます。
rbd ドライバは FUA に対応していないため、QEMU は FUA を「書き込みの後に flush する」ことで代わりに実現します (`block/io.c`)。
flush は librbd のキャッシュを書き出すので、結果として書き込みごとに Ceph まで届いてから返ります。

これは後の計測でも、`writethrough` が `directsync` とほぼ同じ速さになることで確かめられます。

## 実測で確かめる

### 計測環境と測り方

| 項目 | 内容 |
| --- | --- |
| ハイパーバイザ | Proxmox VE 9.2 (QEMU 11.1)、3 ノード、メモリ 251 GB |
| Ceph | 20.2 (Tentacle)。OSD は SATA SSD を各ノードに 4 本、イレイジャーコーディング (2+1) の RBD |
| ネットワーク | ノードごとに 10GbE を 2 本、BGP の ECMP で振り分ける |
| ローカル SSD | SATA SSD (Micron 1100 2TB) をホストから丸ごと VM に渡す |
| ゲスト | Ubuntu 26.04、8 コア、メモリ 4 GiB |
| VM ディスクの設定 | `virtio-scsi-single`、`aio=io_uring`、`iothread=1` |

RBD は librbd (QEMU の rbd ドライバ) でつないでいます。krbd ではありません。

同じ負荷をローカル SSD と RBD にかけ、書き込みの完了、fsync の完了、読み返しの順に比べます。

どちらもゲストから fio でデータ用ディスクに直接アクセスしました。
`--direct=1` でゲストのページキャッシュを避け、モードを変えるたびに qemu を起動し直しています。
RBD は未使用の領域を速く読めるため、計測前に両方のディスクをランダムなデータで埋めました。
各項目の間は RBD で 10 秒、SSD で 20 秒空けました。

### 1 件ずつ書くとき、fsync の有無で何が変わるか

ランダムな位置に 4 KiB ずつ、1 件の完了を待って次の 1 件を書きました。「書き込み」の列では各回の書き込み完了まで、「毎回 fsync」の列では永続化を要求して fsync が返るまで待ちます。
単位はすべて IOPS (1 秒あたりの書き込み回数) です。以下の表では、RBD の `none` と `writeback` は 2 回の平均、それ以外は 1 回分の値を整数に丸めています。

| 設定 | SSD 書き込み | SSD 毎回 fsync | RBD 書き込み | RBD 毎回 fsync |
| --- | ---: | ---: | ---: | ---: |
| `none` | 15,468 | 1,157 | 582 | 548 |
| `writeback` | 21,761 | 1,122 | 7,973 | 574 |
| `writethrough` (参考) | 1,187 | 1,153 | 590 | 581 |
| `directsync` (参考) | 1,226 | 1,196 | 557 | 571 |
| `unsafe` (参考) | 22,386 | 12,331 | 7,926 | 5,837 |

書き込み完了だけを待つと、`none` から `writeback` に変えたときの伸びはローカル SSD で約 1.4 倍、RBD で約 14 倍でした。
RBD では、1 件書くたびにネットワークの先の Ceph を待っていた時間を、librbd のキャッシュで短縮できます。

毎回 fsync すると、ローカル SSD では両モードとも約 1,100 IOPS、RBD ではどちらも 500 台です。
`writethrough` はもともと書き込みごとに永続化を待つので、どちらのディスクでも fsync を加えたときの差は小さくなります。
`unsafe` だけは fsync を加えても SSD で 12,331 IOPS、RBD で 5,837 IOPS です。flush を無視するので、この数値には永続化を待つ時間が含まれません。

### 複数の書き込みを並行すると、どれだけ速くなるか

1 MiB ずつ連続して計 4 GiB を書き、同時に出せる要求数を 1 件から最大 16 件に増やしました。単位はすべて MB/s です。

| 設定 | SSD 1 件 | SSD 最大 16 件 | RBD 1 件 | RBD 最大 16 件 |
| --- | ---: | ---: | ---: | ---: |
| `none` | 300 | 517 | 169 | 758 |
| `writeback` | 2,086 | 3,600 | 1,091 | 1,408 |
| `writethrough` (参考) | 289 | 460 | 200 | 478 |
| `directsync` (参考) | 254 | 489 | 171 | 503 |
| `unsafe` (参考) | 1,654 | 3,550 | 1,072 | 1,410 |

ローカル SSD で 16 件を並行すると、`none` は 517 MB/s、`writeback` は 3,600 MB/s でした。後者はホストのメモリが書き込みを受け取る速さを含みます。
RBD では、並行して要求を出すと `none` でも先の書き込みが終わる前に次を出せます。そのため `writeback` による伸びは、1 件ずつの約 6 倍から最大 16 件の約 1.9 倍に縮みました。
RBD の `writethrough` は同じ 16 件で 478 MB/s です。librbd のキャッシュが有効でも毎回 flush を待つため、`directsync` の 503 MB/s に近い値になりました。

### 同じ範囲を読み返したとき、どちらのキャッシュが効くか

16 MiB の範囲を 4 KiB ずつランダムに読み、同じ範囲で 20 回繰り返しました。

| 設定 | ローカル SSD (IOPS) | Ceph RBD (IOPS) |
| --- | ---: | ---: |
| `none` | 4,960 | 2,496 |
| `writeback` | 29,735 | 2,503 |
| `writethrough` (参考) | 31,581 | 2,529 |
| `directsync` (参考) | 4,964 | 2,515 |
| `unsafe` (参考) | 27,225 | 2,428 |

ローカル SSD では、`none` から `writeback` に変えると約 6 倍になりました。`writethrough` と `unsafe` でも、先に読んだデータをホストのページキャッシュから返せます。
RBD では、5 モードすべてが約 2,400〜2,500 IOPS でした。librbd の既定の `writearound` は、同じ範囲を読み返しても読み取りをキャッシュから返しません。

全 5 モードの各回の値と fio の条件は、[計測データの一覧](https://github.com/negineri/zenn-docs/tree/main/data/proxmox-ve-disk-cache-modes#fio-の結果) にまとめています。

### ローカル SSD では、書き込みが終わったあとも fsync が待たされる

連続書き込みで出た 3,600 MB/s は、SSD 自体の書き込み速度 (約 500 MB/s) を大きく超えています。ゲストに完了が返ったとき、データはどこにあるのでしょうか。

そこで `writeback` で 12 GiB を一気に書き、ホストのメモリのうち書き出しを待っている量 (`/proc/meminfo` の `Dirty`) を 1 秒ごとに記録しました。
ゲストでは約 3.5 GB/s で書き終わりましたが、その直後、ホストの `Dirty` は約 12 GiB に達していました。
qemu の使用メモリ (RSS) は約 1 GB のままで、データはホストのページキャッシュに溜まっていました。

そこから `Dirty` は毎秒約 0.5 GB ずつ減り、約 25 秒でほぼ元の水準に戻りました。
この書き出しと重なるように、書き込みごとに fsync する負荷を 30 秒かけると、175 IOPS でした。
90 秒空けて同じ負荷をかけると 1,127 IOPS です。ゲストが短時間で大量に書けても、その直後に永続化を求める処理には、先に溜めた分の待ち時間が残ります。

ホストでは、書き出しに使えるメモリに対する未書き出し量の割合が `vm.dirty_ratio` に達すると、書き込み元も書き出しを担います。しきい値は空きメモリや回収可能なページの量で変わります。[Linux カーネルの説明](https://docs.kernel.org/admin-guide/sysctl/vm.html#dirty-ratio)
この溜まり方がホスト全体に及ぼす影響は、後の節「なぜ RBD では writeback を勧め、ローカルでは勧めないのか」でまとめます。

### RBD で fsync が返ったデータは qemu を止めても残るか

速度の試験では、毎回 fsync すると `writeback` は `none` に近い値になり、`unsafe` だけが速くなりました。
そこで、ゲストが保存できたと判断したレコードが、qemu の強制終了後にも読めるかを確かめました。

RBD のディスクに ext4 を作り、ゲストで次のことを続けます。

- 4 KiB ほどのレコードに連番とチェックサムを付けてファイルに追記し、1 件ごとに fsync する
- fsync が返るたびに、その連番を SSH で外のマシンに送る (外のマシンが「保存済み」と受け取った番号を覚えておく)
- 同時に、別のファイルに 50 MB/s でランダムに書き込み、キャッシュに未書き出しのデータがある状態にする

20〜60 秒たったところで、ホストで qemu を `kill -9` で止めます。
VM を起動し直し、ファイルを先頭から検査して、受け取った最後の番号までのレコードがそろっているかを見ました。

RBD では、librbd のキャッシュは qemu のプロセスの中にあります。
qemu を止めると、このプロセスが保持していた未書き出しのデータは失われます。今回もホストと Ceph は稼働を続けています。
ローカルのディスクではキャッシュがホストのページキャッシュにあり、qemu を止めても消えないので、この方法では試せません。

30 回試した結果、`writeback` では 10 回とも fsync 済みのレコードがすべて残り、`unsafe` では 5 回中 2 回、末尾の 1〜2 件を失いました。

| `cache=` | 回数 | fsync が返ったデータを失った回数 |
| --- | --- | --- |
| `none` | 5 | 0 |
| `writethrough` | 5 | 0 |
| `writeback` | 10 | 0 |
| `directsync` | 5 | 0 |
| `unsafe` | 5 | 2 |

`none` の最初の 1 回と `writeback` の最初の 5 回は、再起動直後に検査スクリプトが読めませんでした。その分は、後の回で同じファイルを先頭から検査し、保存済みと記録した番号まで照合しています。

`writeback` と `unsafe` では、レコードの検査後に `e2fsck` で ext4 の整合性も調べました。
`unsafe` でレコードを失った 2 回も、ファイルシステムの整合性検査は通っています。

## なぜ RBD では writeback を勧め、ローカルでは勧めないのか

同じ `writeback` でも、キャッシュがどこにあり、どこまで溜まるかがディスクの種類で違います。
その違いが、得られる速さと、引き受ける負担の両方を決めます。

| 観点 | Ceph RBD | ローカル SSD |
| --- | --- | --- |
| キャッシュの置き場所 | qemu のプロセスの中 (librbd) | ホストのページキャッシュ |
| 未書き出し量を制御する単位 | イメージごと (既定のしきい値は 24 MiB) | ホストのメモリ (今回の `Dirty` のピークは約 12 GiB) |
| `none` のときに 1 件の書き込みで待つもの | ネットワークの先の Ceph (約 1.7 ms) | 手元の SSD (約 0.06 ms) |
| 1 件ずつの書き込みの伸び | 約 14 倍 | 約 1.4 倍 |
| 毎回 fsync する書き込みの伸び | ほぼ変わらない | ほぼ変わらない |
| 未書き出し分を保持する場所 | その VM の qemu のメモリ | ホストで共有するページキャッシュ |

### RBD: Ceph の応答待ちが減り、未書き出し量はイメージごとに制御される

RBD の `none` は、書き込みのたびにネットワーク越しに Ceph の応答を待ちます。
`writeback` にすると、この待ち時間を librbd のキャッシュが肩代わりするので、1 件ずつの書き込みは約 14 倍になりました。

書き込みごとに fsync すると、`none` が 548 IOPS、`writeback` が 574 IOPS でした。どちらも永続化を待つため、書き込みだけのときほど差が出ません。
qemu を強制終了した試験でも、`writeback` で fsync 済みのレコードは 10 回分すべて残りました。
未書き出し量をイメージごとに制御できるのが、ローカル SSD との運用上の違いです。ネットワークと Ceph の帯域は他の VM と共有します。

### ローカル: 速くなる部分は小さく、負担はホスト全体に及ぶ

ローカル SSD の `none` は、もともと手元の SSD を待つだけなので速く、1 件ずつの書き込みは `writeback` にしても約 1.4 倍でした。
連続書き込みの 3,600 MB/s や読み返しの約 6 倍は大きく見えますが、前者は SSD に届く前のホストのメモリの速さです。
読み返しの試験ではゲストのページキャッシュを迂回しました。通常のファイル読み取りではゲストにもデータが残り、同じ内容をホストと二重に持つ場合があります。

その代わり、次の負担をホスト全体で引き受けます。

#### ホストのメモリを使う

ゲストに割り当てたメモリとは別に、ホストのメモリを使います。
12 GiB 書いたとき、qemu の RSS は変わらず、ホストの `Dirty` だけが約 12 GiB 増えました。

#### fsync が急に長く待たされる

12 GiB を書いた直後は、ホストの `Dirty` が元の水準に戻るまで約 25 秒かかりました。その間に測った毎回 fsync する書き込みは 175 IOPS で、落ち着いた後は 1,127 IOPS でした。
この試験で記録したのは 30 秒間に処理できた件数です。個々の fsync やデータベースのコミットに何秒かかったかは測っていません。

#### 同じディスクと同じホストを巻き込む

書き出しの間、そのディスクの待ち行列は書き出しで埋まり、同じディスクにある他の VM も待たされます。
未書き出しのデータが上限に近づくと、カーネルは書き込むプロセスを止めて待たせます。
この上限はホスト全体で共有しているので、その VM と関係のないプロセスも止まることがあります。

#### ホストの電源断で失う量が大きい

qemu を止めてもホストのページキャッシュは残ります。ホストごと電源が落ちれば、そこにしかないデータは失われ得ます。
今回の約 12 GiB はホストで観測した未書き出し量です。電源断による損失量は測っていません。

### 起動ディスクでの試験中にホストが再起動した

同じディスクとホストを巻き込む問題は、ホストの起動ディスクと同じ SSD では特に深刻です。
Proxmox VE の既定のストレージ `local-lvm` は起動ディスクの上にあるので、いちばん踏みやすい組み合わせです。

筆者は最初、この `local-lvm` (安価な SATA SSD) で測り、ホストを 1 台止めてしまいました。
同じディスクで `none` と `writeback` を交互に流したときの記録です。

| 時刻 | モード | 起きたこと |
| --- | --- | --- |
| 20:02〜 | `none` | 異常なし |
| 20:26〜20:37 | `writeback` | 毎回 fsync する書き込みが 0 IOPS。20:35 に HA のサービス (pve-ha-lrm) の処理が 45 秒止まった |
| 21:00〜 | `none` | 異常なし |
| 21:12〜 | `writeback` | 21:21 に HA の watchdog が切れ、ノードが再起動 (fencing) された |

この環境では、`writeback` の回に fsync を伴う処理と HA の処理がともに滞りました。別の SSD で観測した `Dirty` の推移から、起動ディスクへの書き出しとホスト側の I/O が競合した可能性を考えています。再起動した瞬間の待ち行列の内訳までは分かりません。
同じ症状を調べるときは、対象 VM とホストのルートが同じ物理ディスクを使うかを確認し、`Dirty` の増減と HA のログの時刻を突き合わせます。`none` でも同じ SSD の帯域は共有するので、I/O の多い VM は起動ディスクから分ける方が安全です。

### それでもローカルで writeback を使うなら

一時的なファイルを大量に書く VM などで、`writeback` の速さが欲しいこともあります。その場合は次のようにします。

- ホストの起動ディスクとは別のディスクに置く
- ホストの `vm.dirty_bytes` と `vm.dirty_background_bytes` を小さくし、書き出しを早める (ホスト全体に適用される)
- ホストの `Dirty` を監視する
- Proxmox VE のディスクの帯域や IOPS の上限 (`mbps_wr`、`iops_wr` など) で、VM が発行する書き込みの量を制限する

## 先行事例

2021 年の記事「[OpenStackでCephを使う場合のディスクキャッシュ設定について](https://zenn.dev/tj/articles/0002-cache-settings-in-kvm-ceph)」は、QEMU 4.2 と Ceph Nautilus のソースと資料を読み、次のことを示しています。

- QEMU のキャッシュモードが `ceph.conf` の `rbd_cache` を上書きする
- QEMU の `write-cache` は librbd に渡らないので、RBD では `writeback` と `writethrough` の区別に本質的な意味はない

1 つ目は、本記事で読んだ QEMU 11.1 でも同じでした。
2 つ目は、今回の計測とは合いませんでした。
`write-cache` が librbd に渡らないのはそのとおりです。
しかし QEMU のブロック層が書き込みごとに FUA を付け、それを flush で代わりに実現するため、`writethrough` は実際に書き込みごとに Ceph まで届きます。
`writethrough` が `directsync` と同じ速さで、`writeback` よりずっと遅いことがその表れです。

また、Ceph は Octopus から `rbd_cache_policy` が入り、既定値が `writearound` になりました。
読み取りがキャッシュから返らないのはこのためです。

## RBD のディスクを writeback に変更する

対象 VM の停止を伴うため、ゲストをシャットダウンできるタイミングで変更します。

1. Proxmox VE の管理画面で対象 VM の「ハードウェア」を開く。ディスクのスロット (例: `scsi1`)、ストレージ名、ボリューム名を確認し、変更する RBD イメージを特定する。
2. その VM をシャットダウンし、停止を確認する。対象ディスクの編集画面でキャッシュを「Write back」に変更して保存する。似た名前の「Write back (unsafe)」は flush を無視する設定である。
3. VM を起動する。管理画面で同じスロットのディスクに `cache=writeback` が適用されていることを確認する。

ホストのシェルから確認する場合は、`qm list` で対象 VM の ID を調べ、`qm config 101 --current` の `101` をその ID に置き換えて実行します。
対象スロットの行に、変更前と同じボリューム名と `cache=writeback` があれば、意図したディスクへの設定を確認できます。
