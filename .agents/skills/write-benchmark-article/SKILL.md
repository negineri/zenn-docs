# 実測から設定を選べる記事を書く

## 書き始める前に

手元の原稿、計測条件、生データから、次の問いへの答えを整理する。推敲では著者の語り口と実体験を生かす。

- 読者は何を選ぶのか。通常の推奨は何で、どの条件で答えが変わるか。
- その条件で挙動が変わるのはなぜか。処理を受ける場所や、完了を返すタイミングはどう違うか。
- 違いを確かめるには、同じ条件でどの値とどの値を比べればよいか。
- 利点を得た代わりに何が後に残るか。その負担はいつ、誰に及ぶか。

## 判断を先に示し、根拠を順に読ませる

1. **タイトルと冒頭で選択を示す。** タイトルには読者が判断できるようになることを入れる。冒頭で基本の選択と例外を示し、安全に使うための条件と、性能上の利点が出る条件を書き分ける。
2. **推奨が分かれる軸で仕組みを対比する。** たとえばローカル SSD と Ceph RBD で結論が違うなら、両方について「データをどこに置くか」「何を待って完了を返すか」に答える。後の実測でも同じ軸を使う。判断に必要な用語は初出で、誰が何を求め、何を待つ操作なのかを短く説明する。
3. **実測は一つの問いごとにまとめる。** 表の前に、何を変え、何をそろえ、何を測ったかを書く。表に単位を付け、複数回の値をまとめたら集計方法を記す。主に比べる値を隣り合わせにし、本文で解釈に使う参考設定にも対応する値を載せる。直後に、注目する差とその理由を書く。全試行の値やスクリプトは、本文からたどれる場所にまとめる。
4. **実測から冒頭の推奨を導く。** 倍率に加え、元の設定で待っていた処理、変更で短くなった待ち時間、後に残る処理まで説明する。たとえば「ゲストに書き込み完了が早く返った」という結果は、どこまで書けた時点の計測なのかを添えると、ディスクへの永続化にかかる時間と区別できる。メモリ消費や他の利用者への影響も、選択を左右する場合はここで結び付ける。

障害事例を使う場合は、条件、観測した症状、結果を時系列で示す。記録で確認できた事実と、そこから推定した原因を書き分ける。プロセス停止とホスト電源断のように試験対象が違う場合は、どこまで確かめたかを明記する。推奨から外れる選択に用途がある場合は、それが役立つ条件や負担を抑える方法も示す。

## 読み返すとき

冒頭だけで、想定読者が自分の条件に合う選択を言えるか。順に読めば、表の下の解説から前の節へ戻らずに数字を解釈できるか。最後には、条件が変わるとなぜ推奨も変わるのかを、仕組みと実測の両方から説明できるかを確かめる。
